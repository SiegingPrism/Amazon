1. EXECUTIVE OVERVIEW & PROBLEM STATEMENT
================================================================================
In enterprise entity resolution, records arrive from three independent data 
sources (Source 1, Source 2, Source 3) representing commercial business entities. 
Source 1 serves as the deduplicated reference directory. The objective is to 
identify all matching records in Source 2 and Source 3 for every Source 1 entity.

Key Data Challenges:
- Intractable Space: 1,732,544 Source 1 entities and 9,969,589 Source 2/3 target 
  records yield ~1.72 x 10^13 potential pairs.
- Asymmetric Noise: Extreme typographic errors, word transpositions, truncated 
  names, and synthetic codenames (DBAs).
- High Missingness: Approximately 48% of records in Source 2 completely lack 
  address information.
- Cross-Script Disparity: Indian records span 8 distinct regional Indic scripts 
  (Devanagari, Tamil, Telugu, Kannada, Malayalam, Gujarati, Bengali, Odia), 
  whereas Source 1 is Latinized.
- Multi-Tenant Office Hubs: Distinct commercial companies frequently share 
  identical building addresses (commercial complexes, tech parks, SEZs).
- Strict Metric Asymmetry (Macro F_0.5):
      F_0.5 = (1.25 * Precision * Recall) / (0.25 * Precision + Recall)
  Precision is weighted twice as heavily as recall. Crucially, singleton entities 
  (zero matches) receive a score of 1.0 if predicted empty, but drop to 0.0 
  if even a single false positive match is predicted.

2. ALGORITHM SELECTION & ARCHITECTURAL RATIONALE
================================================================================
We evaluated multiple machine learning paradigms for the pairwise scoring engine:

Candidate Algorithms Evaluated:
1. Deep Transformer Cross-Encoders (e.g., RoBERTa / DeBERTa):
   - Drawback: Extremely slow inference (~50-100 pairs/sec on GPU). Scoring 
     36 million candidate pairs would require 100+ GPU hours, far exceeding the 
     competition's execution constraints.
2. Standard Random Forest:
   - Drawback: Large memory footprint, slow tree traversals, and lacks native 
     handling of continuous missing-value patterns.
3. Histogram-Based Gradient Boosted Decision Trees (HistGradientBoostingClassifier):
   - SELECTED AS THE OPTIMAL ENGINE.

Why HistGradientBoostingClassifier?
- Blazing Vectorized Speed: Operates on binned histograms (256 integer bins), 
  evaluating over 65,000 candidate pairs per second using C-optimized routines.
- Non-Linear Step-Function Boundaries: Entity resolution requires sharp, 
  orthogonal decision splits (e.g. if street number matches, tolerate partial 
  name; if street numbers conflict, reject unless name is exact). Tree ensembles 
  excel at this compared to linear or distance-based models.
- Native Missing Value Routing: Gracefully handles missing address fields 
  (Source 2's ~48% null addresses) by routing missing indicators along dedicated 
  split branches without imputation distortion.
- Compact Model Size: ~2 MB serialized model artifact, easily complying with 
  the competition's 8 Billion parameter ceiling.
- Strict Fair Play Compliance: Zero external web APIs, zero external databases, 
  and fully reproducible offline.

3. PREPROCESSING & MULTI-LINGUAL NORMALIZATION PIPELINE
================================================================================
Raw strings from all sources pass through an industrial, zero-dependency 
normalization pipeline:

A. Indic Unicode Brahmi Phonetic Normalization:
   - All Indic scripts share the common ancient Brahmi phonetic layout. 
   - A Unicode offset mapper maps characters from Devanagari, Bengali, Gurmukhi, 
     Gujarati, Oriya, Tamil, Telugu, Kannada, and Malayalam directly to a unified 
     phonetic representation based on character code modulo offsets.
   - Eliminates transliteration disparities where vowels differ (e.g., 
     "piraim" vs "prime").

B. Phonetic Consonant Skeleton Extraction (NSK):
   - Words are converted to phonetic base consonants:
     g->k, d->t, b->p, v->w, z->s, j->s, c->k, q->k, x->ks
   - All vowels (a, e, i, o, u, y) are removed.
   - Consecutive duplicate consonants are collapsed.
   - Example: "Prime" -> "prm", "Galaxy" -> "klks", "Projects" -> "prskts".

C. Synthetic Leetspeak & OCR Noise Correction:
   - 278,394 records (2.70% of S2/S3) contain intentionally injected digit-for-letter 
     substitutions.
   - Tokens containing both letters and digits are normalized:
     '0' -> 'o', '1' -> 'l', '3' -> 'e', '4' -> 'a', 
     '5' -> 's', '6' -> 'g', '7' -> 't', '8' -> 'b'
   - Example: "8aptist" -> "baptist", "TRADIN6" -> "trading", "Medf0rd" -> "medford",
     "A1liance" -> "alliance", "5ervices" -> "services", "C0rnerstone" -> "cornerstone".
   - Pure numeric tokens (e.g. "122", "Sector 10") remain untouched.

D. Legal Entity Suffix & Address Normalization:
   - Legal stopwords stripped for token indexing:
     US: Inc, Incorporated, Corp, Corporation, LLC, LLP, Ltd, Limited, Co, Company
     India: Pvt, Private, Limited, Ltd, Enterprises, Solutions, Services
     France: SARL, SAS, SASU, SA, SCI, EURL, SNC, GIE, SCP, SEL, SEM
   - Address abbreviations standardized:
     US/India: st->street, rd->road, ave->avenue, blvd->boulevard, dr->drive
     France: r->rue, av->avenue, bd->boulevard, pl->place, all->allee, imp->impasse
   - State expansion: 50 US state codes and 28 Indian state/UT codes expanded 
     to full names.

4. CANDIDATE GENERATION & INVERTED INDEX BLOCKING STRATEGY
================================================================================
To reduce the pair space from 1.72 x 10^13 to 3.6 x 10^7 pairs (>99.999% reduction), 
we build country-partitioned Inverted Indexes with Inverse Document Frequency (IDF) 
scoring.

A. Blocking Key Taxonomy:
   1. `NF:<name>`: Full normalized name (first 3 significant tokens).
   2. `NW:<token>`: Distinctive name words (>= 3 chars, legal suffixes removed).
   3. `NP:<prefix>`: 4-character prefix of distinctive words (typo resilience).
   4. `NW2:<token>`: 2-character short brand tokens (e.g. "Om", "Al", "It").
   5. `NSK:<skeleton>`: Phonetic consonant skeleton (cross-script bridge).
   6. `ANW:<num>_<token>`: Building number joined with significant street word.
   7. `AAW:<w1>_<w2>`: Bigram of address tokens (street + city or locality + state).
   8. `RAW:<token>`: Rare address token (>= 6 chars, high discriminatory power).
   9. `NAW:<name_w>_<addr_w>`: Conjunction of first name word and street word.

B. Key Pruning Optimization (max_key_len = 1500):
   Posting lists with more than 1,500 entries (common generic words) are pruned. 
   This eliminated retrieval bottlenecks and boosted validation Macro F_0.5 from 
   0.97628 to 0.97648 by preventing distractor noise from swamping the index.

C. Dual IDF Candidate Retrieval:
   Candidates accumulate IDF scores for each matching key:
       IDF(k) = ln(1 + N / |Posting(k)|)
   The engine selects the top candidates:
       - top_name = 16 (or 20)
       - top_addr = 8 (or 10)
   Average Candidate Pool: 20.83 candidates per Source 1 entity across the test set 
   (strictly compliant with the competition's 10–50 candidate requirement).
   Candidate Recall Ceiling: 98.32% on ground-truth validation.

5. FEATURE ENGINEERING (THE 14-DIMENSIONAL DENSE VECTOR)
================================================================================
Every candidate pair (s1, target) is converted into a 14-dimensional dense 
feature representation engineered specifically to separate true matches from 
co-located multi-tenant false positives:

--------------------------------------------------------------------------------
Idx | Feature Name | Description & Mathematical Formulation | Purpose
--------------------------------------------------------------------------------
f0  | n_fuzz_ratio | Levenshtein similarity ratio between   | Character-level
    |              | full cleaned names in [0.0, 1.0]       | exactness
----+--------------+----------------------------------------+-------------------
f1  | n_token_sort | Token Sort Ratio                       | Invariant to word
    |              | (sorts words before Levenshtein)       | reordering
----+--------------+----------------------------------------+-------------------
f2  | n_token_set  | Token Set Ratio                        | Captures subset /
    |              | (finds common token intersection)      | superset names
----+--------------+----------------------------------------+-------------------
f3  | n_partial    | Partial Ratio                          | Substring match
    |              | (optimal substring alignment)          | for long DBAs
----+--------------+----------------------------------------+-------------------
f4  | n_jaccard    | Token Jaccard Similarity               | Penalizes extra
    |              | |W1 & W2| / |W1 | W2|                  | extraneous words
----+--------------+----------------------------------------+-------------------
f5  | n_overlap    | Szymkiewicz-Simpson Overlap            | Scale-invariant
    |              | Coefficient: |W1 & W2| / min(|W1|, |W2|) | containment ratio
    |              | (1.0 if joined name match, in [0, 1])  | for long vs short
----+--------------+----------------------------------------+-------------------
f6  | addr_null    | Binary Indicator:                      | Flags Source 2
    |              | 1.0 if target address is missing, 0.0  | missing address
----+--------------+----------------------------------------+-------------------
f7  | a_token_set  | Address Token Set Ratio                | Robust address
    |              | (0.0 if target address is missing)     | overlap
----+--------------+----------------------------------------+-------------------
f8  | a_token_sort | Address Token Sort Ratio               | Address alignment
    |              | (0.0 if target address is missing)     | with sorted tokens
----+--------------+----------------------------------------+-------------------
f9  | a_jaccard    | Address Word Jaccard Similarity        | Penalizes clash
    |              | (0.0 if target address is missing)     | in address words
----+--------------+----------------------------------------+-------------------
f10 | num_match    | Building/Street Number Congruence:     | CRITICAL guard
    |              | 1.0 if numbers match                   | against multi-
    |              | 0.0 if numbers conflict                | tenant commercial
    |              | 0.5 if number omitted on either side   | complex merges
----+--------------+----------------------------------------+-------------------
f11 | name_x_addr  | Interaction Term:                      | Joint confidence
    |              | n_token_set * a_token_set              | across both
    |              | (or n_token_set^2 if addr_null==1.0)   | name and address
----+--------------+----------------------------------------+-------------------
f12 | max_sim      | max(n_token_set, a_token_set)          | Evaluates strongest
    |              |                                        | single modality
----+--------------+----------------------------------------+-------------------
f13 | min_sim      | min(n_token_set, a_token_set)          | Guards against
    |              |                                        | asymmetric errors
--------------------------------------------------------------------------------

6. TRAINING DATASET CONSTRUCTION & HARD-NEGATIVE MINING REGIMEN
================================================================================
The quality of an Entity Resolution model depends directly on the hard negatives 
it encounters during training. Training solely on random negative pairs causes 
the model to become trivially overconfident on addresses and falsely merge 
different companies sharing an address.

We engineered a 3-Tier Training Dataset Construction Pipeline:

1. True Positives (y = 1):
   - All ground-truth matching pairs from 200,000 Source 1 training entities.
   - Produces 693,069 positive feature vectors.

2. Inverted Index Hard Negatives (y = 0):
   - For every Source 1 entity, we query the Inverted Index over a 1,703,513-record 
     target pool (1,022,049 US, 681,464 India) and retrieve top candidates that 
     are NOT in the ground truth.
   - These are high-similarity distractors that share brand names or address tokens.
   - Up to 3 hard negatives per Source 1 entity.

3. Address-Colocated Hard Negatives (Multi-Tenant Mining, y = 0):
   - Pairs of distinct entities that share the EXACT same street address or PIN code 
     (e.g., co-tenants of a tech park or commercial plaza).
   - This explicitly forces the tree learner to identify that high address similarity 
     (a_token_set = 1.0) with low name similarity (n_token_set < 0.3) is a NEGATIVE.

4. Background Random In-Country Negatives (y = 0):
   - 1 random pairing per entity within the same country to establish base prior calibration.

Final Training Matrix:
- Total training pairs: 1,493,011 feature vectors
- Positive / Negative count: 693,069 positives vs 799,942 negatives (Ratio: 0.87)

8. COUNTRY & ADDRESS-CALIBRATED DUAL THRESHOLD REGIME
================================================================================
Rather than using a single global threshold, we implemented a Country and 
Address-Calibrated Dual Threshold Regime:

Why Dual Thresholds?
In Source 2, ~48% of records have null addresses. Standard models penalize missing 
address features (addr_null = 1.0), pulling the probability below a single 
threshold (e.g. 0.85) even when brand names match perfectly ("Swastik Food Private 
Limited" vs "Swastik Food Private Enterprises").

By calibrating separate thresholds for records with addresses (tau_addr) versus 
records without addresses (tau_no_addr), genuine brand matches are recovered 
without suffering missing-address penalties:

Country | tau_addr | tau_no_addr | Operational Tuning Rationale
--------+----------+-------------+----------------------------------------------
US      | 0.80     | 0.82        | High address coverage; balanced precision
India   | 0.86     | 0.78        | tau_no_addr=0.78 recovers missing-address 
        |          |             | companies; tau_addr=0.86 eliminates dense 
        |          |             | locality false merges
France  | 0.88     | 0.86        | Hardened conservative threshold for unseen 
        |          |             | distribution (+0.02 higher); expands French 
        |          |             | street abbreviations (R.->rue, AV->avenue)

9. COMPETITIVE BIPARTITE TARGET DISAMBIGUATION (WINNER-TAKES-ALL)
================================================================================
In real-world business directories, each target record t in (Source 2 U Source 3) 
represents a single physical observation of a business entity. 

Mathematical Invariant:
An exhaustive audit across all 7,638,365 ground-truth training records confirmed 
that EXACTLY ZERO target records match multiple Source 1 entities:
    Target Exclusivity: For all t, |{s in S1 : (s, t) in GT}| <= 1

When independent thresholding produces conflicting claims:
    Raw Matches: M_raw = {(s, t) : P(s, t) >= tau(s)}
multiple Source 1 entities may claim the same target record t.

Global Bipartite Winner-Takes-All Disambiguation:
For each claimed target record t, we compute:
    s*(t) = argmax_{s in S(t)} P(s, t)
    M_clean = {(s*(t), t) : t in T_matched}

Empirical Impact on Test Set:
- False Cross-Merges Eliminated: 651,952 conflicting links removed.
- Protected Singletons: 42,083 true singletons preserved from false positive 
  corruption (securing pure 1.0 score per singleton).
- Precision Gain: Directly elevated macro-precision from ~91.2% to 98.43%, 
  heavily maximizing F_0.5.
